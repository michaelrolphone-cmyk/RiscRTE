# Catalog preservation and fault qualification 1.0.0

Reusable qualification procedure, deterministic fixtures and evidence records.
Hardware-test status: **not tested**.

A paired update passes only when **every required manifest file** has the exact
length and SHA-256 and remains usable by its target consumer after the final
firmware step and supported restart. Per-file serial operations must cause **zero
unrelated changes**. Failed, incomplete or unverified effects cannot be reported
as successful. Measure actual firmware-flash erasure separately against declared
behavior; there is no blanket claim that all settings survive every flash.

## Package and preparation

- `matrix.json`: 46 cases with explicit variants, stimuli, expected results and evidence.
- `fixtures.py`, `inventory.json`: deterministic bytes, lengths, CRC32 and SHA-256.
- `result-template.json`: unexecuted rows for every case/variant.
- `review_result.py`: fail-closed report-consistency checker against an exact manifest.
- `test_qualification.py`: tests of these preparation/report tools.
- `conformance.json`: preparation evidence, separate from device results.

Python 3.10+ standard library is sufficient:

```sh
python3 docs/catalog-preservation/1.0.0/fixtures.py --check
python3 docs/catalog-preservation/1.0.0/test_qualification.py
python3 docs/catalog-preservation/1.0.0/fixtures.py --materialize /tmp/preservation-fixtures-NEW
cp docs/catalog-preservation/1.0.0/result-template.json /tmp/preservation-run-NEW.json
```

The materialization path must not already exist. Generated bytes are test inputs,
not a deployable payload or a namespace mapping. Use the pinned payload semantic
validator on each real candidate before mutation; the report checker does not
replace it.

## 1. Bind the run and determine applicability

Record run ID/timestamps, operator, device/hardware revision, host/browser, client
source, exact firmware-before/after identities, numeric upstream release ID,
catalog revision, manifest/container hashes and lengths, complete inventory hash,
firmware artifacts, flash method and order. Freeze the release and trusted profile
for the run. Record actual provider path/component/capacity bounds and write budget.

Obtain explicit trusted `(firmware_id, volume) -> namespace_id` and target-consumer
evidence. Compare HELLO/NS results with the profile. IDs are positive opaque uint64
values, represented as decimal strings; backend labels, physical mount paths and
provider instances never route uploads. Enumeration proves admission, not live
availability. Missing, ambiguous, unavailable or read-only transfer mappings fail
without fallback. A read-only **final** mapping may suffice for verification/use.

Choose disposable individual destinations disjoint from sentinels. Record exact
namespace-relative UTF-8 bytes. Do not prepend physical roots, normalize case,
Unicode or escapes, or silently switch create/replace modes. List every required
parent and check ancestor-first. Only authoritative NOT_FOUND justifies a single
MKDIR; a file occupying a parent is a conflict. Flat providers use root-only paths.

Determine applicability from actual capabilities and declared scope. An unsupported
product feature can be not applicable with reason and capability evidence; that
does not impose an implementation requirement. Required protocol/fault coverage
must still be exercised in an identified software harness and linked as substitute
coverage if the physical product cannot safely or meaningfully exercise it. Label
mixed evidence accordingly. Software substitutions never stand in for physical
final readback, restart persistence and consumer usability when hardware success
is claimed. The supported-order variant of final usability must be physical for
hardware acceptance; invalid-order and readonly-final variants may be harness tests.

## 2. Establish independent preservation oracles

Before **each serial interval**, including negative/fault tests, observe:

1. Selected target existence/type/length/full hash, or authoritative absence.
2. An unrelated same-parent sibling; a sibling-directory file where supported;
   and the complete known test-tree inventory.
3. A user file outside payload paths, read through its actual independent owner/consumer.
4. A persistent non-default native setting, read through its independent owner/UI/export.
5. An unrelated admitted-namespace sentinel where one exists.

Use generated sibling/user-file bytes for disposable sentinels. Record sentinel
ID, kind, independent observer, owner/route, namespace/path or setting key, and
length/SHA-256 or canonical setting value. A file named settings is not a settings
sentinel. Preserve actual user data with the product's backup/test procedure.
Keep confidential setting evidence in the approved private test record. Exclude
only specifically declared independently justified volatile fields, never broad
normalization that hides changes.

Do not use the failing uploader's cache, echoed source hash or progress UI as the
oracle. Use native-owner reads, instrumented provider snapshots or a separately
verified read path once custody is safe. RTEF1 has no directory-listing command;
use a known full test inventory or an independent supported inventory mechanism.
Inspect unexpected creation/deletion/renaming, type/directory and content changes.
If coverage is partial, name its exact scope and keep broader claims unverified.

For each serial-only interval, save S0 immediately before and S1 immediately after.
Save S2 after supported restart. Require no unrelated changes between S0/S1/S2.
Do not combine this interval with flashing. For flashing save F0 immediately before
and F1 immediately after and compare the declared volume/settings effects separately.
When flash occurs first, take a fresh S0 after flash and before payload mutation.
Flash erasure cannot be attributed to serial operations or hide their effects.

The result format represents each sentinel definition as:

```json
{"id":"preferences","kind":"settings","route":"native settings owner",
 "observer":"independent observer","independent":true,"flash_scope":"settings"}
```

A snapshot has `id`, `stage`, `timestamp`, `firmware_id`, `observer`, `environment`,
`evidence`, and `inventory`. Inventory entries have `id` and `state`. File state is
`{"exists":true,"type":"file","bytes":49,"sha256":"..."}`; absent state uses
`{"exists":false}`. Settings state is `{"persistent":true,"value":...}`. Include
all declared sentinels in each snapshot. Retain the full source snapshots and diff;
a claimed zero count alone is not proof. `flash_scope` is the manifest logical
volume or `settings`, not a backend routing label. Record additional independently
observed scopes explicitly rather than pretending they are admitted volumes.

## 3. Run boundary, binary and path cases

Fixture bytes are `byte[i] = (i * 73 + seed) mod 256`. Sizes are 0, 1, 47, 48, 49,
257 and 4097. The 257-byte fixture covers every possible byte, including NUL, LF,
CR, DEL and 0xff. The 4097-byte fixture spans 86 maximum-size RTEF1 chunks.

For each create/readback case: snapshot S0, PATH, PUT create, bounded WRITE,
COMMIT IEEE CRC32, GET/READ/CLOSE, compare exact length and complete SHA-256, then
snapshot S1. Empty still requires PUT/COMMIT and GET/CLOSE, without WRITE/READ.
Advance CRC, offsets and progress only by acknowledged/actual byte counts. Positive
short I/O is legal; continue the unconsumed suffix after acknowledged short writes.
Zero progress before completion is failure. No text/newline conversion.

Preseed 4097-byte targets for shorter/empty replacement. Replacement truncates at
PUT, is destructive/non-atomic and requires an existing regular file. Verify exact
49 or zero bytes and absence of stale suffixes. Create is exclusive. Existing-create
and missing-replace failures never authorize an automatic mode switch. Exercise
all exact-path and invalid-path variants within the provider's stricter limits;
the 511-byte wire bound alone is insufficient.

## 4. Inject faults and recover explicitly

Every matrix variant needs a reproducible fault point and observable hook. Retain
harness revision/invocation for software injection. For lost PUT/COMMIT ACKs prove
the command executed and the response was suppressed; omitting execution is a
different test. Record attempted/acknowledged offsets, exact status, target/custody
state, all later commands, progress output and bounded deadline/memory measurements.

| Class | Required result/recovery |
| --- | --- |
| Positive short I/O | Continue actual acknowledged count; queued bytes do not count. |
| Definite failure, known handle/custody | Fail; pinned client's best-effort ABORT may close that handle; record its result. |
| Timeout/disconnect/malformed or mismatched reply, uncertain offset, -6, -10 | Client unusable; no cleanup request, automatic retry, reconnect, reset or overwrite. |
| Clean BUSY/UNAVAILABLE/DENIED/NO_SPACE | Failure, not absence/success. Distinguish pre-dispatch busy from safety loss during I/O. |
| Retained/uncertain provider custody | Fence I/O, preserve dependencies until real restart; host close or elapsed time proves no recovery. |
| Lost PUT ACK | Target may already be truncated; preserve unverified result, inspect custody/path before recovery. |
| Lost COMMIT ACK | Target may be complete; no blind upload; separate safe full readback may reconcile the state. |

ABORT cannot delete a partial create, restore replaced bytes or undo prior files.
Healthy open transfers temporarily fence sleep/restart/USB handover; close or
commit successfully before handover. This is distinct from terminal retention.
RTEF1 has no reset command. The 30-second idle budget permits cleanup only at a
safe checkpoint and is no guarantee of immediate cleanup.

Stop the dependent update after uncertainty and preserve evidence. Determine safe
custody through the supported product recovery procedure. Retained custody requires
real restart before reinspection. Send no diagnostic commands through the unusable
client session. After explicit recovery, begin a fresh nonzero session at sequence
1, reconfirm firmware/mapping and inspect the selected destination. A partial create
needs an explicitly reconciled replacement choice. Append a separate recovery
record linked to the immutable original; never rewrite an uncertain attempt as
though its ACK arrived. Server immediate exact-request replay is a separate direct
harness test, not a client retry guarantee.

## 5. Verify complete payload, flash effects and final use

Run trusted manifest/container shape, semantic and byte validation before mutation:
complete inventory, source hashes, parents, operations, mappings and compatibility.
Check previous ownership/size/hash guards when supplied; omitted guards do not
create new prerequisites. Freeze the required-file denominator. Deliberately fail
the last required file and reject omitted/duplicate/tampered inventory. Earlier
verified files and side effects remain visible; combined status stays incomplete.

Use only a supported declared flash order:

- Firmware, payload, verify: disclose actual initial/factory erasure, confirm the
  running target firmware and rediscover its admission before serial mutation.
- Payload, firmware, verify: require explicit preservation evidence for **every**
  required destination across the exact method/transition. Reject unknown/erased
  effects before mutation. Finish healthy transfers before handover; then reconfirm
  firmware/mapping and read every required file. Final mapping may be read-only.

Compare F0/F1 against actual declared effects. Declared-preserved mismatches fail.
Unknown is uncertainty, never preserving-update evidence. Frozen Wave/T-Watch
factory images erase device data and offer no data-preserving update kit. Report
settings erasure separately from per-file preservation.

After the final firmware step and supported restart, fully read back every required
file with exact size/SHA-256 and successful CRC/CLOSE. Exercise the actual target
consumer for each resource, or provide a consumer load/validated-inventory trace
covering every required file. Record consumer/app version, operation and per-file
evidence. Merely writing an opaque private serial root does not establish usability.
Recheck unrelated sentinels through their owners after restart. Record restart kind
and timing; cold-start/power-cycle tests are distinct and no single result proves
universal power-loss durability.

## 6. Result records and consistency check

Case statuses: `pass`, `failed`, `unverified`, `not_run`, `not_applicable`. A fault
case passes when the expected error/recovery behavior was observed. Fill every named
variant, environment and evidence reference. A failed transfer is not automatically
a failed qualification case. Preserve unresolved failures and all limitations.

Use `evidence_class` = `software-injection`, `hardware`, or `mixed`; environments
are `software-injection` or `hardware`. Software-only records retain
`hardware_status: not_tested`. Mixed records need actual physical final readback,
restart and consumer observations to mark hardware confirmed. Source/software/
publication/hardware fields stay separate. `qualification_status: complete_evidence`
is a report-completeness label, not automatic hardware approval.

A required row marked not applicable needs a `substitute_coverage` object containing
pass status, software-injection environment, evidence, serial snapshot references
and all named variant observations. Capability-specific path cases can instead
carry an evidenced not-applicable result without substitute coverage.

Each file result is keyed by exact manifest volume/destination and includes:

```json
{"volume":"trusted-volume","destination":"/file.bin","operation":"create",
 "expected_bytes":49,"actual_bytes":49,"expected_sha256":"...","actual_sha256":"...",
 "commit_acknowledged":true,"readback_close_acknowledged":true,"readback_crc_match":true,
 "after_last_firmware_step":true,"after_restart":true,"consumer_usable":true,
 "environment":"hardware","status":"verified","evidence":["immutable receipt/readback/consumer evidence"],
 "original_attempt_id":"run/file/attempt1","recovery_receipt":null}
```

For lost COMMIT ACK, leave `commit_acknowledged` false. A separate recovery receipt
must contain `original_status` failed/unverified, `original_receipt`, `run_id`,
`explicit_recovery`, `safe_custody`, `fresh_session`, `independent_full_readback`
(all true), and evidence. This records a deliberate recovery, not an automatic
retry or deletion of the original failure. Record actual counts/hashes on failure.

`flash_artifact_hashes` contains the exact manifest firmware artifact records,
including ID/source/bytes/SHA-256. Flash `declared`/`observed` are lists of
`{"scope":"logical-volume-or-settings","effect":"preserved|erased|unknown"}`;
observed may additionally be `changed`. Declared effects must match the manifest.
Unknown declarations stay explicit; an observed unknown cannot verify a declared
preserved/erased effect. Include evidence and distinct before/after flash snapshots.
Final totals derive only from verified final records. Every case's `serial_snapshots`
references distinct before/after snapshots; restart and flash use their own pairs.

```sh
python3 docs/catalog-preservation/1.0.0/review_result.py \
  /tmp/preservation-run-NEW.json --manifest /path/to/pinned/manifest.json
```

Exit 0 means the supplied record is internally complete under this matrix; exit 1
means failed/incomplete/inconsistent. The pristine template must fail. The checker
cannot authenticate evidence, infer truthful hardware observations, validate
arbitrary referenced artifacts or replace the pinned payload semantic validator.
Review actual logs/readbacks/consumer evidence before recording the product result.
Keep prior failed runs and linked recoveries even after a later run passes.

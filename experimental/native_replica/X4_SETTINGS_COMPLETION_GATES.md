# X4 SD-first settings: product completion gates

This is an experimental source checkpoint, not an enabled product or a firmware
delivery. The original hardware-protocol evidence preserves the frozen X4 .99 source cohort.
The source union now also reconciles the .101/.102 System/Files lineage, shared
text hosts, RTC fixes and checked native FileSource handoff; all native
persistence selections remain default-off.
Watch has no SD and is excluded from this selection.

## Everyday path being completed

Ordinary preferences and multiple saved Wi-Fi profiles share the checked native
Core used by their actual readers and writers. A completed native transaction
preserves the edit and its intent together. At a settled Runtime checkpoint, the
selected SD provider publishes and verifies a complete image before acknowledging
the captured native prefix. On a subsequent boot with erased native state, the
typed SD restore must complete before an app reads authoritative preferences or
Wi-Fi. While blank native storage awaits discovery, applications may use visible,
temporary read-only defaults; they cannot persist those defaults as recovery.

A successful save receipt is native durability. `exitSafe()` is custody safety.
Neither alone proves that the latest edit has reached SD. An externally forced
full native erase before SD acknowledgement can still lose those pending edits.
Existing update paths must be distinguished by what they actually erase; an
ordinary update that preserves native storage is not the same operation.

## Demonstrated source paths

- Actual Settings controllers save ordinary settings, and Wi-Fi Settings saves
  two distinct profiles through Runtime's public atomic broker. Fresh readers
  recover their bytes after complete native-artifact erase and typed SD restore.
- Home/Quick, automatic low-battery actions, Home rules and a claimed preset have
  corresponding controller-to-SD campaigns. Explicit, automatic and rollback
  origins remain distinct; reading a value never manufactures an edit.
- Battery broadcast, BLE aliases/radio compensation and explicit/automatic
  Contexts use the same broker. Their exact source and evidence are recorded in
  the aggregate qualification index, rather than inferred from a shared helper.
- Normal SD synchronization, interrupted publication and retained ownership are
  exercised through actual Runtime/CpuPort/X4/FatFs source. Ordinary file reads
  and raw USB export admission are rechecked between attempts. These are not
  executions of the complete Files and USB applications on physical hardware.
- Actual startup and owner checkpoints are bound behind the X4-only lifecycle
  selection. Source-pinned target probes measure control sizes and local frames;
  host tests measure payload demand. See the lifecycle, maintenance and resource
  documents beside this one for the exact scope of each result.
- The settled-save follow-on fences new maintenance while either resident
  invocation holds a live atomic grant, drains accepted custody independently,
  and attempts each namespace once after the last release or final revocation.
  Twenty-five real lifecycle/Runtime/X4/FatFs cases pass normally and under
  ASan/UBSan. Available SD is acknowledged for both namespaces at those settled
  boundaries; unavailable/busy SD preserves the pending native edits.

Synthetic SD sectors, ESP-IDF NVS/RTOS shims, controller UI/radio/clock providers
and deliberately prepared source datasets remain explicit test inputs. Host
passes and target compilation are not hardware or private-filesystem approval.

## Refusals versus decisions

Two genuinely competing datasets are preserved unchanged. Examples include an
unrelated SD lineage or an independent native legacy dataset beside an existing
SD dataset. Choosing or merging those sources needs an explicit decision; no
"newest timestamp wins" or silent replacement is implemented.

The exact selected native export marker and committed RTENSD1 index define
interrupted-write recovery. Following that format-defined authority is not a
choice between independent datasets. Corrupt-present, unknown, oversized or
unavailable sources retain their bytes and refuse/defer; these conditions do
not justify silently selecting a fallback or asking the user to approve an
unverified dataset as valid.

The catalog has finite work and inventory bounds, not unlimited history. The
qualified one-page fixture admits 5,761 retained generations; generation count
alone is not the general capacity contract. The next such fixture exceeds the
1,048,576 returned-entry work ceiling and refuses without writing. Actual file
names, pages, ordinary files and provider latency affect capacity and time.
No automatic garbage-collection/deletion policy is introduced as a completion
requirement. See the resource and interrupted-catalog evidence for exact bounds.

## Measured everyday-history latency concern

The real dispatcher protocol is measured separately from physical-card speed.
The original benchmark, before bounded collect-and-next scheduling, is retained
as the comparison baseline:
With 1, 10 and 100 retained one-page generations in each namespace, the next
paired checkpoint takes 222, 298 and 1,898 owner polls; total queued SD operations
are 68, 104 and 876. Synthetic blocked time is 262, 368 and 2,607 milliseconds.
At 100 generations, a single namespace save takes 949 polls, 438 operations and
1,303 synthetic milliseconds while leaving the other namespace unchanged.
Five independent repetitions agree on counts and outcomes. Host wall time is
recorded separately and is not target latency. All tested checkpoints succeed.

At 100 generations, 99 historical page names exceed the 64-entry sorted window,
requiring two full directory traversals for each inventory scan. This is a
practical latency concern, not a tested capacity failure or a demand for unlimited
history. Physical SD timing, cancellation and UI/watchdog behavior remain product
activation gates. Baseline evidence is in `evidence/native-settings-history/`.

The subsequent bounded native catalog step queues one next entry immediately
after collection. It adds no loop, fields, I/O, history policy or authority. With
identical operation counts, the 100-generation single checkpoint now uses 541
owner polls and 791 synthetic milliseconds; the paired checkpoint uses 1,082
polls and 1,583 milliseconds. Five normal and sanitized repetitions agree. This
removes idle scheduler turns but leaves physical-card latency and responsiveness
unqualified. See `CATALOG_POLL_BUDGET.md` and `evidence/catalog-poll-fusion/`.

## Selected target resource results

The initial full link's 42,472-byte IQ overlap and a feasible 8,512-byte worker
stack path are preserved as failed evidence. Both concrete defects are repaired:
large copied requests/results, publication verification and atomic payloads now
use the explicit whole-range-checked PSRAM allocator without INTERNAL fallback.
Atomic/mailbox/task controls and unchanged 8 KiB worker stacks remain INTERNAL.

The final selected native link and unchanged fixed IQ proof pass. Static DRAM
is 77,392 bytes (+4,928 over the delivered baseline), permanent settings INTERNAL
requests are 29,917 bytes before allocator metadata, IRAM is unchanged, and
8,448 bytes remain before the unchanged IQ bank. Runtime metadata is 322,312
PSRAM bytes. The audited linked worker call-chain lower bounds fall to 4,464
and 3,248 bytes; these are not whole-stack maxima or measured high-water.

The complete fourteen-case real-path fixture peaks at 264,833 raw PSRAM request
bytes, including checked-allocator overhead. Deliberately full-size legacy import
peaks at 595,428 logical payload bytes, excluding allocator headers/vendor heaps.
Neither is a universal device-memory bound. Heap-region ceilings, allocation
failure paths, exact wrapper addresses and source-stable target receipts are in
`docs/SETTINGS_NATIVE_RESOURCE_LINK_20261012.md` and
`docs/SETTINGS_ATOMIC_PAYLOAD_PSRAM_20261012.md`.

Remaining activation gates are the exact selected multi-repository product
composition and physical free/largest-block/stack high-water, latency/watchdog,
card removal/swap and power-loss qualification. Source and host/target results
do not authorize enabling an unqualified product or moving IQ/audio buffers.

## Saved-network privacy

Replicas contain the opaque settings map, including saved Wi-Fi credential bytes.
This format adds integrity/recovery checks, not encryption; anyone who can read
the card may read those bytes. Test credentials are synthetic and never sourced
from a user's device. Keep card backups private. Full native erase recovery
must not depend on an encryption key that the same operation would erase.
